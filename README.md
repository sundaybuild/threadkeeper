# ThreadKeeper 脆存档

Chrome 扩展：**把你在 Threads 上发过的内容完整存下来** —— 串文、回复、图片、视频，外加一个双击就能翻看的离线网页。

> 非 Meta 官方出品，与 Meta Platforms 无关。这是个人数据备份工具，请只用它导出你自己的内容。

## 它存下什么

```
下载/ThreadKeeper/<你的账号>/
├── posts.json     完整结构化数据
├── index.html     离线存档页，双击就能看
└── media/         所有图片和视频的原始文件
```

`index.html` 是个自包含的时间线：按时间倒序排列，能搜正文、能按「串文/回复」筛选，图片视频直接内嵌播放，跟着深浅色主题走。断网也能看。

## 安装

1. Chrome 打开 `chrome://extensions`
2. 右上角打开「开发者模式」
3. 点「加载已解压的扩展程序」，选中本文件夹
4. （可选）点图钉把它固定到工具栏

## 使用

> ⚠️ **第一次用之前**：打开 `chrome://settings/downloads`，把「**下载前询问每个文件的保存位置**」关掉。不关的话，几百个媒体文件会逐个弹出保存对话框。

1. 打开自己的主页，例如 `https://www.threads.com/@你的用户名`
2. 点扩展图标，勾选想要的内容，点「开始存档」
3. 进度显示在页面右下角，弹窗关掉也不影响

| 选项 | 默认 | 说明 |
|---|---|---|
| 只抓新内容 | 开 | 跟上次存档比对，抓到旧的就停。第二次之后只要几秒 |
| 包含我的回复 | 关 | 自动切一下「回复」标签去抓，耗时大约翻倍 |
| 包含别人给我的回复 | 关 | 逐条串文抓回复区，慢得多，见下方说明 |
| 下载图片和视频 | 开 | CDN 链接几周就失效，存成本地文件才算备份 |
| 生成离线网页 | 开 | 产出 `index.html` |

### 关于「别人给我的回复」

#### ⚠️ 用之前先做一次：随便点开你自己的一条串文

打开自己主页，点进任意一条串文，等下面的回复区显示出来，然后回到主页开始存档。

**每个账号只需要做这一次**，扩展会记住。忘了做也不会出错——它会提示你，并跳过这一项、把其他部分照常跑完。

**为什么要这一步**：读回复区需要知道 Threads 内部那个查询长什么样。这个项目的原则是**不把 Meta 的任何内部查询 ID 写进代码**——那既是把逆向白纸黑字写进仓库，也会随 Meta 发版失效，变成需要一直追着改的东西。所以扩展选择现学：你点开串文的那一刻，页面自己会发一次请求，它顺手学会并记下来。哪天 Meta 改版让记下来的失效了，它会自动清掉并再提示你点一次。

#### 为什么这一项特别慢

前两种抓的是时间线，一次翻页拿一大批；**别人的回复得逐条串文去问**——有多少条有回复的串文，就至少有多少次请求。两个优化会省掉大部分：只请求 `reply_count > 0` 的串文，以及回复数跟上次比没变过的直接跳过。所以只有第一次慢，之后每次只补新增的那几条。

每条串文最多抓 5 页回复（约 100 条）。抓下来的挂在 `posts[].incoming_replies`，离线网页里折叠显示，搜索也能搜到里面的内容。

#### 一次可能抓不齐，多跑几次

串文多的话，这一项要连着发几百个请求，**很容易被 Threads 限流**。被限流时它不会报错，而是返回 HTTP 200 加一个空的回复列表——跟「这条串文本来就没人回」长得一模一样。

所以扩展一律把空结果当成「没有新消息」：不记录、不更新回复数快照、下次再来一遍。**这一项是可以反复跑的，只增不减**，每跑一次补一批。

跑完浮层会告诉你还剩多少条没拿到：

```
收到的回复 526 条
92 条没拿到回复（被限流，或回复已删）
下次会再试一遍，仍是空的就不再试了
```

隔十几分钟再跑一次，跑到那个数字变成 0 或很小就齐了。同一条串文若连着两轮都是空的，就不再重试了——那多半是回复已被作者删除，再试也是空。

两种情况会让这一项提前收手，其余部分都照常导出：

- **连续 10 条都是空的** —— 多半正被限流，这时等再久也是空，而退让又让每条越等越久，跑完几百条要十几分钟且颗粒无收。不如停下，过十几分钟再跑。已抓到的一条不丢。
- **连续 3 条直接报错** —— 查询本身失效了（Meta 改版），会清掉记住的查询并提示你重新学一次。

### 想推倒重来

扩展弹窗最下面有「清空这个账号的存档，下次从头抓」，点两下确认即可。清掉的是浏览器里存的历史记录（含增量比对用的快照），下载目录里已有的文件不受影响，下次存档会覆盖同名文件。

清空后媒体也会重新下载一遍——这是有意的：万一你手动删过下载目录，保留下载记录会导致那些文件再也补不回来。

**如果提示「没能捕获到数据请求」**：在主页上点一下「回复」标签、再点回「串文」，然后重新存档。原因见下面的原理。

## 存档范围

- ✅ 你发的**原创串文**：正文、时间、点赞/回复/转发数、图片视频、外链预览
- ✅ 同一串里你自己的接续楼层，放在主贴的 `continuation` 字段
- ✅ 你在别人串下的**回复**（可选），并记下回复的是谁、原话是什么
- ✅ **别人在你串文下的回复**（可选），挂在对应串文的 `incoming_replies`
- ❌ 自动跳过转发别人的内容（跳过条数记在 `skipped_reposts`）

**已经删掉的帖子会留在存档里。** 增量存档只做合并、不做删除 —— 上次存过、这次抓不到的条目会保留下来，这正是存档的意义。

## 原理

Threads 的网页数据走 Meta 的 GraphQL 接口，请求里带一个 `doc_id`，这个 ID 会随 Meta 发版变化，写死必然过期。

所以扩展不写死任何接口参数，而是：

1. `interceptor.js` 在页面世界里挂钩 `fetch` 和 `XMLHttpRequest`，**偷听**页面自己发出的主页请求，把 URL、请求头、`doc_id`、`variables` 整套存成模板（串文、回复、单帖回复区各存一份）
2. 点存档后，把模板里的分页游标 `after` 重置为 `null`，从第一条开始，带着页面自己的登录态一页页重放，直到 `has_next_page` 为 false
3. 响应结构也不写死路径，而是递归找出 `{edges, page_info}` 形态的连接对象再解析

抓单帖回复区时还多一步：模板里的帖子标识（可能是长数字 `pk`，也可能是 shortcode）会被逐条替换成目标串文的，而请求头和 token 借用最新那份主页模板，免得存久了失效。

这样即使 Meta 换了 `doc_id` 或调整了字段嵌套，扩展一般仍能工作。

「没能捕获到数据请求」是因为直接刷新落地主页时首屏由服务端直出，页面还没发过 GraphQL 请求。扩展会自动切标签、自动滚动去触发；实在触发不到时，手动切换一下标签页一定会发请求。

## 权限说明

| 权限 | 用来干什么 |
|---|---|
| `storage` + `unlimitedStorage` | 存历史存档，用于增量比对和跨次合并。全部留在本地 |
| `downloads` | 把 JSON、网页和媒体文件写到下载目录 |
| `www.threads.com` / `.net` | 只在 Threads 主页上运行 |

没有任何数据离开你的浏览器：不上传、不经过第三方服务器、不收集统计信息。

## 已知限制

- 只在 `www.threads.com` / `www.threads.net` 网页版生效，需要已登录
- 媒体是逐个下载的，几百个文件会在 Chrome 下载栏刷出一长串条目（功能不受影响）
- 抓取间隔 0.65 秒（回复区 0.9 秒）、失败自动重试 3 次；被限流时会提前收手，隔一会儿重跑即可
- 单次上限 600 页，够绝大多数账号
- 依赖 `world: "MAIN"` 内容脚本，需要 Chrome 111+
